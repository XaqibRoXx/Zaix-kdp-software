# Zaxis KDP — Windows Installation, Portable Use & Recovery

## Release artifacts

The Phase 4 release workflow produces:

- MSI installer.
- NSIS installer executable.
- portable `Zaxis-KDP-Portable.exe` package.
- SHA-256 manifest.
- installer/portable smoke-test evidence.

Verify the release SHA-256 manifest before distributing or installing a build.

## Normal installation

The MSI is the preferred managed Windows installation.

1. Close older Zaxis KDP instances.
2. Run the MSI.
3. Launch **Zaxis KDP**.
4. Open **Cloud & Server**.
5. Enter the server API URL.
6. Use the one-time connection code generated by the server installer or an authenticated Owner/Admin session.
7. Confirm the app reports the connected user and healthy diagnostics.

The raw desktop API token is stored with Windows user-bound encryption rather than normal app/localStorage settings.

## Upgrade

For an installer-based upgrade:

1. Ensure current work is saved/synced.
2. Keep a recent server backup.
3. Install the newer release.
4. Launch the app and verify project access, fonts, cache, and cloud sync.
5. If the server was restored or credentials were intentionally revoked, pair the device again.

The Phase 4 CI performs a silent MSI install and uninstall smoke on a clean GitHub Windows runner before a release candidate passes.

## Uninstall

Use Windows **Installed apps / Apps & features** or the MSI uninstall path.

Cloud projects remain on the server. Server backups are not removed by uninstalling the desktop application.

Before removing local-only projects, confirm they have been synced/exported or otherwise backed up.

## Portable package

Keep the portable package folder together:

```text
Zaxis-KDP-Portable.exe
app-data/
PORTABLE.txt
STARTUP-SMOKE.txt
```

Tauri-managed portable application data uses the local `./app-data` directory for this flavor.

Security-sensitive cloud credentials may still use Windows user-bound protected credential storage. Therefore, “portable” means the application/runtime data package can move as a folder; it does not mean encrypted credentials can be copied to another Windows user or machine.

After moving the portable folder to another PC, pair that PC separately.

## Local cache and recovery

Settings exposes:

- cache limit;
- cache location;
- native cache status;
- clear native cache;
- clear local recovery cache.

Cloud-first projects should be recoverable from server revisions. Clearing local caches should not be used as a replacement for proper server backup/restore.

## Large books

Phase 4 includes a 400-page stress gate. The editor artboard navigator renders a small nearby thumbnail window instead of hundreds of heavy thumbnail nodes at once, while a lightweight jump selector keeps every artboard directly accessible.

For best performance with image-heavy books:

- use cloud/editor proxies for large originals;
- keep native cache on a drive with adequate free space;
- use the configured cache limit rather than unbounded local storage;
- keep originals in the Cloud Asset Library.

## Signed auto-update

Settings → **Auto Update** exposes:

- Check for Updates.
- available version/release notes.
- signed download progress.
- Install.

Production updater packages are generated by the **Signed Windows Release** workflow and must pass Tauri signature verification before installation.

See `docs/UPDATER_RELEASE.md` for signing-key setup and the N → N+1 verification procedure.

Unsigned normal QA builds can still compile/run, but a production auto-update channel is not considered complete until a signed release has been published and an installed older version successfully updates to the next signed version.

## Cloud reconnect after server restore

A server backup restore intentionally invalidates old API tokens and pairing codes.

After restore:

1. Generate a new one-time connection code from the restored Owner/Admin environment.
2. Windows app → **Cloud & Server**.
3. Pair again.
4. Verify identity and diagnostics.
5. Open a project and allow queued work to reconcile.
6. If the server revision differs from an offline queued base revision, use the explicit conflict workflow rather than overwriting silently.

## Troubleshooting

### Server connection fails

Check:

- HTTPS API URL is correct.
- server diagnostics/health endpoint is reachable.
- connection code is not expired or already consumed.
- cPanel firewall/WAF is not blocking API methods.
- server `ALLOWED_ORIGINS` retains the Tauri origins.

### Cloud token stopped working after restore

Expected behavior. Pair again with a new one-time code.

### Portable app starts but has no previous account

Expected on a different Windows user/machine when encrypted credentials cannot be decrypted there. Pair the new machine.

### Background removal unavailable

Normal editing does not depend on the optional image worker. Verify worker URL/secret and Admin worker diagnostics if AI image processing is required.

### Update check says channel is unavailable

Only signed release builds with a configured updater public key + HTTPS endpoint can use the production update channel. Verify the signed release workflow and `latest.json`.

## Release acceptance

Before distributing a Windows release candidate, require:

- desktop TypeScript/Vite build green;
- dependency security audit green;
- large-book QA green;
- offline/sync regressions green;
- KDP regressions green;
- PDF regressions green;
- server/worker gate green;
- backup/restore integration green;
- Windows installer build green;
- MSI silent install/uninstall green;
- portable startup green;
- SHA-256 evidence generated;
- for updater releases: signed N → N+1 update verified.
